## KI-001：云端鉴权服务未部署，改密码功能当前不可用

| 项目 | 内容 |
| --- | --- |
| 严重级别 | **高**（功能不可用，但非阻断性——不影响登录、不影响添加账号） |
| 状态 | **未解决**（代码已就绪并验证，待部署云端） |
| 目标版本 | 下一次版本更新时随云端部署一并处理 |
| 首次记录 | 2026-09-12（1.4.1 发布后） |
| 关联文档 | `docs/RELEASE_1.4.1.md` §5、§7.3 |

### 影响

1.4.1 发布后，用户在「个人设置 → 修改密码」点提交会收到 **「接口不存在」**，
密码不会被修改。

**不受影响的功能**：登录、退出、添加闲鱼账号（默认密码门禁已在 1.4.1 移除）、
IM 长连接、商品/订单同步。

### 现状证据（已在生产核实）

云端鉴权服务代码位于 `/opt/gemstory/xianyu-auth/`，实测内容：

```
auth_store.py  47184 bytes  Sep 11 17:03
server.py      14367 bytes  Sep 11 17:03
change_password:      auth_store=0  server=0   ← 1.4.1 新增，不存在
revoke_user_sessions: auth_store=0  server=0   ← 1.4.1 新增，不存在
reset_password:       auth_store=1  server=0   （数据层有，未暴露）
health:               {"ok": true, "service": "xianyu-auth"}
```

请求路径与失败点：

```
前端「修改密码」
  → 后端 POST /api/v1/auth/change-password
  → cloud_auth_request("change_password", ...)
  → 云端 server.py:252 未知动作 → 404 {"ok": false, "message": "接口不存在"}
  → CloudAuthError(status_code=404)
  → 后端 HTTPException(404, "接口不存在")
  → 前端提示「接口不存在」
```

### 根因

**两层原因，第二层是真正的设计缺陷：**

1. **运维层**：主流水线（`.github/workflows/build-and-publish.yml`）**不部署
   `deploy/cloud_auth/`**（全文件搜索无任何相关步骤），必须手工部署，而这次没部署。
2. **设计层**：客户端与云端是**两个可独立上线的组件**，但后端 `change_password`
   的云端转发**假定云端已支持该动作**，没有做顺序无关的兼容，也没有给出可理解的
   提示。因此「先发客户端、后更新云端」这个合法顺序会导致功能裸奔报错。

### 修复方案

**A. 部署云端（必需，约 2 分钟，不涉及数据库表结构变更）**

完整命令与回滚见 `docs/RELEASE_1.4.1.md` §5.3 / §5.5。要点：

1. 备份 `/var/lib/gemstory/xianyu-auth/server.db` 与两个 `.py` 文件
2. **整目录上传** `deploy/cloud_auth/`（历史陷阱：只传部分文件会让目录混入陈旧
   `admin.html`）
3. `sudo cp` 覆盖 `/opt/gemstory/xianyu-auth/` 下的 `.py`
4. `sudo systemctl restart xianyu-auth`，验证 `health` 与 `grep -c change_password`

**B. 补顺序无关兼容（建议一并做）**

后端 `change_password` 在收到云端的「接口不存在 / 404」时，不要把它当普通失败抛出，
而应识别为**云端版本过旧**，返回明确提示，例如：

> 云端鉴权服务版本过旧，暂不支持自助修改密码，请先更新云端服务或联系管理员。

判定依据建议用响应体 `message == "接口不存在"` 或 `code`/HTTP 404 组合，
避免把「动作存在但因参数错返回 404」误判（当前云端不存在这种情形，但约定要写清）。

同时补充一条：**云端不支持时不应回退到「只改本机」**——那正是 1.4.0 及更早版本
误导用户的根源（提示成功但登录无效）。当前实现已经是「不修改本机」，保持即可。

### 验收标准

1. 云端 `grep -c change_password` 在 `auth_store.py` 与 `server.py` 均 ≥ 1
2. 应用界面点「修改密码」：
   - 原密码填错 → 提示「原密码不正确」，密码不变
   - 新密码与原密码相同 → 提示「新密码不能与原密码相同」
   - 正确修改 → 提示「云端密码已更新，请重新登录」并退出登录
3. **新**密码可登录，**旧**密码不可登录
4. 改密码前已登录的其他设备会话失效，需重新登录
5. 云端用户数与部署前一致（本次改动不涉及用户表）

### 备注

该问题的修复代码**已包含在 v1.4.1 中并通过验证**，缺的只是**部署这一步**：

- 云端动作已用本地独立实例 + 真实 HTTP 验证 8 项全过（`docs/RELEASE_1.4.1.md` §3.2）
- 后端转发由 33 个单元测试覆盖
- 因此部署本身不需要再改代码

## KI-002：发布顺序缺少约定，客户端可能先于云端上线

| 项目 | 内容 |
| --- | --- |
| 严重级别 | 中（流程问题，会导致 KI-001 这类功能裸奔） |
| 状态 | **未解决** |
| 目标版本 | 下一次版本更新 |
| 首次记录 | 2026-09-12 |

### 影响

当一次版本同时包含**客户端改动**与**云端鉴权服务改动**时，若只发布了客户端，
依赖云端新能力的功能会直接报错（如 KI-001 的「接口不存在」），
而云端改动**没有任何版本号可供比对**，排查时也无从判断线上云端是哪个版本。

### 根因

1. 云端鉴权服务**自身没有版本号**（代码中无 `VERSION` / `x.y.z` 字样，
   管理页显示的「版本」是各客户端上报的诊断版本，不是云端自身版本）
2. 没有「本次版本是否需要同步更新云端」的检查清单，发布流程里也没有这一步
3. 两个组件共用一台服务器但属于不同 systemd 服务 / 目录，容易在沟通中被混为
   「云端」一个概念

### 修复方案（建议）

1. **给云端鉴权服务加版本号**：例如 `AUTH_SERVICE_VERSION` 常量 + `/health`
   返回该字段，并在 `deploy/cloud_auth/` 部署时写入；这样一眼能看出线上云端版本
2. **发布清单加一条**：每次发版前确认「本次改动是否涉及 `deploy/cloud_auth/`」，
   涉及则**先部署云端、再发客户端**（或在代码层做 KI-001 的 B 方案兼容）
3. **发布文档模板固定两栏**：「客户端侧变更」/「云端侧变更」，各自列出部署动作

### 验收标准

1. `/health` 返回云端服务版本号，且与仓库 `deploy/cloud_auth/` 的版本一致
2. 发布文档中能明确区分客户端侧与云端侧变更及其部署状态
