# 闲鱼管理系统全面重构与功能补全工作方案

## 1. 工作目标

本次工作的目标不是继续增加接口数量，而是将当前系统整理为可追溯、可运行、可验证的独立版本。

最终必须同时满足以下要求：

1. 清除旧仓库作者、仓库地址、推广入口、激活体系、旧项目路径及其他无关信息。
2. 对继承或完全一致的前端文件逐一处置，形成独立实现或完成明确的许可证合规处理。
3. 将旧版功能逐项映射到真实业务实现，不再用通用记录、固定成功、空数组或等待连接冒充完成。
4. 账号、商品、订单、聊天、自动回复、发布、擦亮、登录续期和卡密发货等核心链路能够在真实账号下闭环运行。
5. 所有页面、按钮、接口、后台任务都有对应测试结果和可核查证据。

## 2. 当前基线

审计确认的当前状态如下：

- 当前前端共检查 248 个源码或配置文件，其中 184 个与旧仓库文件逐字节一致，约占 74.2%。
- 当前后端 OpenAPI 共暴露 1025 个操作，其中 585 个来自旧版兼容层，占约 57.1%。
- 兼容层中的部分接口只保存 `FeatureRecord`、返回固定状态、空列表或 `waiting_for_connection`，不能视为真实功能。
- 人脸核验、共享扫码、验证码、群二维码、服务重启、公开公告、支付和部分分析接口尚未形成真实闭环。
- Docker 服务、前端构建和 Python 编译当前可以通过，47 个主要页面能够加载，但这只证明系统可运行，不代表业务完整。

因此，本项目不得继续使用“路由数量一致”作为完成标准，后续统一以“真实业务结果 + 可复现测试证据”为准。

## 3. 工作原则

### 3.1 禁止假实现

以下情况一律标记为“未实现”或“部分实现”：

- 只创建本地记录，没有执行目标业务。
- 固定返回成功、运行中、已完成或空列表。
- 按钮弹出成功提示，但数据和外部平台没有变化。
- 真实功能依赖外部配置，但界面没有配置入口或状态检查。
- 后台任务只生成任务日志，没有执行闲鱼平台操作。
- 接口存在，但请求或返回结构与页面需求不一致。

### 3.2 真实功能必须可证明

每项功能至少保留以下证据：

- 请求接口、关键参数和脱敏后的返回结果。
- 本地数据库变更前后对比。
- 页面显示结果。
- 涉及闲鱼平台时，提供闲鱼端实际结果或可重复验证步骤。
- 失败场景必须显示明确原因，不得吞掉错误。

### 3.3 测试数据隔离

- 使用专用测试账号、测试商品、测试订单和无效卡密。
- 发布、擦亮、发货、回复、退款等动作必须在授权的测试范围内进行。
- Cookie、Token、卡密、API Key 和买家信息不得写入日志、文档或测试报告。
- 删除、批量操作和真实付款测试必须提前确定目标范围。

## 4. 总体实施阶段

## 阶段一：冻结基线与建立功能台账

### 工作内容

1. 冻结当前可运行版本，记录镜像、配置和数据库结构。
2. 提取旧版前端菜单、页面、按钮、接口和后台任务清单。
3. 提取重构版对应清单，建立逐项映射表。
4. 每个功能标记为：
   - 已真实实现
   - 部分实现
   - 仅兼容壳
   - 未实现
   - 明确废弃
5. 标记功能依赖：闲鱼账号、远程 Token、WebSocket、调度器、通知渠道、支付服务或第三方验证器。

### 交付物

- 《功能一比一对照台账》
- 《接口实现状态台账》
- 《外部依赖与配置清单》
- 《测试数据和测试账号范围》

### 通过标准

- 旧版每个菜单、页面按钮、接口和任务均有唯一对应项。
- 不允许出现“其他”“暂未确认”等无法追踪的模糊分类。

## 阶段二：旧仓库痕迹与代码来源处置

### 工作内容

1. 对 184 个完全一致的前端文件逐个登记和分类。
2. 将业务页面、组件、接口封装、状态管理、导航和样式重新设计并独立实现。
3. 删除不再需要的旧入口：
   - 与业务无关的公开推广、下载和远程控制入口
4. 清理文档中的旧仓库绝对路径、旧服务名和旧项目说明。
5. 扫描源码、注释、图片、构建产物、环境模板和数据库初始化数据中的旧信息。
6. 根据实际代码来源补充适当的 LICENSE、NOTICE 和第三方依赖说明；涉及许可证判断时单独进行合规复核。

### 交付物

- 《旧仓库痕迹处置清单》
- 新版导航、布局和公共组件
- LICENSE/NOTICE 或独立实现说明
- 哈希复检报告

### 通过标准

- 源码和构建产物不包含历史署名、历史仓库地址、旧推广域名和旧绝对路径。
- 除通用配置文件和合法第三方依赖外，不再存在与旧仓库完全一致的业务源码文件。
- 删除的入口无法通过菜单或直接 URL 再次访问。

## 阶段三：拆除通用兼容壳

### 工作内容

1. 对 585 个兼容接口按实际使用情况分类。
2. 页面仍在调用的接口必须迁移到专用路由和专用服务。
3. 已有专用实现的接口删除重复兼容注册，避免路由覆盖和 OpenAPI 混乱。
4. 已废弃接口返回明确的 `410 Gone` 或产品定义的废弃错误，不再静默保存记录。
5. 暂未完成的接口返回明确的“未实现/未配置”，不得返回成功。
6. 为每个迁移接口补充请求模型、返回模型、权限检查和错误码。

### 优先处理模块

1. 账号登录、二维码登录、Cookie/Token 续期。
2. 在线聊天、自动回复、AI 回复和消息统计。
3. 商品同步、订单同步、商品发布和图片上传。
4. 卡券绑定、库存预留、付款触发、自动发货和发货记录。
5. 一键擦亮和六小时自动擦亮。
6. 通知渠道、风控日志和数据看板。
7. 商品监控、采集、下单账号和分销链路。
8. 公告、反馈、广告、支付、人脸核验和共享扫码。

### 交付物

- 专用业务路由和服务实现
- 废弃接口清单
- OpenAPI 差异报告
- 接口契约测试

### 通过标准

- 在用页面不再命中 `legacy_surface` 通用兜底。
- 不存在“写一条 FeatureRecord 就提示业务成功”的接口。
- OpenAPI 中每个在用接口都有准确的业务标签、模型和错误码。

## 阶段四：核心业务链路打通

### 4.1 账号与登录

- 扫码登录后创建或更新真实账号。
- 同步昵称、头像、闲鱼账号标识、在线状态和登录有效期。
- 登录态到期前自动续期，失败时通知并要求人工扫码。
- 本地和远程 Token 获取方式均有状态检查、超时和错误提示。

验收：扫码后账号可上线；服务重启后可恢复连接；过期前能自动续期；失败原因可见。

### 4.2 商品与订单同步

- 定时及手动同步商品、订单和状态。
- 防止重复同步任务互相冲突。
- 商品详情、擦亮状态、发布状态和关联卡券保持一致。

验收：闲鱼端变化能在规定时间内同步到系统；重复任务不产生重复数据或错误状态。

### 4.3 在线聊天与自动回复

- 接收实时消息并正确更新已读状态。
- 支持精确、包含、模糊或正则匹配，并在界面明确选择匹配模式。
- 自动回复内容同时写入聊天记录、回复日志、仪表盘和账号统计。
- AI 配置提供地址、密钥、模型、超时、代理和连接测试入口。

验收：测试账号发送消息后，在规定时间内收到回复，系统四处统计结果一致。

### 4.4 商品发布

- 图片上传返回可用于闲鱼发布的有效地址。
- 分类推荐、分类属性、规格和行政区位置完整可填写。
- 发布能力检查失败时给出可操作的修复提示。
- 发布成功后自动同步商品；失败时保留平台原始错误的脱敏摘要。

验收：单品和批量发布均有至少一次真实成功记录，闲鱼端可看到商品。

### 4.5 擦亮

- 开启时立即执行一次。
- 开启后每六小时执行一次。
- 只对符合条件且未达到限制的商品执行。
- 结果以闲鱼端状态为准，不以本地任务提交成功为准。

验收：点击后闲鱼端实际发生擦亮；日志记录具体商品、平台结果和下次执行时间。

### 4.6 卡密自动发货

- 商品与卡券绑定必须可验证和持久化。
- 付款事件触发库存锁定、模板渲染、分段发送和记录落库。
- `{DELIVERY_CONTENT}` 按购买数量自动取用对应数量的未使用卡密。
- 发送失败可重试，且不会重复消耗卡密。
- 退款、取消和异常订单有明确处理规则。

验收：使用测试订单完成付款事件模拟和授权的真实订单测试，买家收到正确分段消息，库存与记录一致。

## 阶段五：外围功能补全

按以下顺序处理：

1. 通知渠道真实发送和测试。
2. 风控日志统计、防止除零和空值显示。
3. 公开公告和弹窗公告读取真实启用记录。
4. 数据分析接口执行真实聚合，不只创建完成记录。
5. 共享扫码完成二维码、协作人、账号登录结果交接。
6. 人脸核验接入明确的验证提供方和回调。
7. 验证码/极验接入真实服务，未配置时自动关闭入口。
8. 支付、充值、提现和广告付款接入真实支付方式；如不需要则完整下线。
9. 服务状态改为真实健康检查，重启操作通过部署编排实现。

## 阶段六：自动化测试与全按钮冒烟

### 自动化测试层级

1. 单元测试：模板渲染、关键词匹配、库存预留、状态转换、统计计算。
2. 接口契约测试：鉴权、请求参数、返回结构、错误码和权限隔离。
3. 服务集成测试：后端、WebSocket、调度器、MySQL、Redis 联动。
4. 页面测试：所有路由加载、表单校验、弹窗、分页、筛选和按钮状态。
5. 真实链路测试：扫码、同步、聊天、回复、发布、擦亮和发货。

### 按钮验收规则

每个按钮必须记录：

- 所在页面和按钮名称。
- 调用的接口。
- 是否修改本地数据。
- 是否调用外部平台。
- 成功结果。
- 失败结果。
- 回滚或恢复方式。
- 测试日期和证据位置。

### 通过标准

- 所有可见按钮均有测试记录。
- 不允许无响应按钮。
- 不允许成功提示与实际结果不一致。
- 删除和批量操作必须有二次确认。
- 页面无 `undefined`、空白错误页和未处理异常。

## 阶段七：发布验收

发布前必须同时通过：

1. 前端生产构建。
2. Python 编译和测试套件。
3. Docker 全服务健康检查。
4. 数据库迁移和备份恢复测试。
5. 旧仓库痕迹复检。
6. 接口兼容壳复检。
7. 主要业务真实账号回归。
8. 安全检查：密钥、Cookie、Token、卡密和个人信息不泄露。

任何核心链路未通过时，不得标记为正式完成。

## 5. 建议执行批次

### 第一批：必须立即处理

- 184 个旧前端文件的来源处置和独立重写。
- 删除与业务无关的推广、下载和远程控制入口。
- 建立完整功能与接口台账。
- 阻止兼容层返回假成功。
- 修复商品同步并发冲突和公开公告固定空列表。

### 第二批：直接影响经营

- 登录续期和在线状态。
- 在线聊天、自动回复、AI 回复和统计。
- 商品发布、图片、分类和行政区。
- 擦亮真实执行。
- 卡密付款触发和自动发货。

### 第三批：扩展和管理功能

- 监控、采集和分销。
- 通知、风控和数据分析。
- 公告、反馈和广告。
- 共享扫码、人脸核验、验证码和支付。

## 6. 进度管理

功能台账中的每一项使用以下状态：

- `待分析`
- `待开发`
- `开发中`
- `待接口测试`
- `待页面测试`
- `待真实链路测试`
- `已通过`
- `明确废弃`

只有同时完成代码、接口、页面和真实业务验证后，才能标记为“已通过”。

每天输出：

- 当日完成项。
- 新发现问题。
- 阻塞项和所需配置。
- 自动化测试结果。
- 第二天处理范围。

每个批次结束输出：

- 功能完成率。
- 真实实现接口数量。
- 剩余兼容接口数量。
- 按钮通过率。
- 已知风险和回滚方案。

## 7. 最终完成定义

项目只有在以下条件全部满足后才算完成：

- 旧仓库痕迹处置通过复检。
- 所有保留功能都有真实专用实现。
- 核心链路在测试账号和授权真实账号下均通过。
- 所有可见按钮完成冒烟测试。
- 所有失败场景有明确提示和可恢复方案。
- 文档、代码、接口和实际运行结果一致。
- 不再使用接口数量、页面可打开或任务已创建作为功能完成证明。
