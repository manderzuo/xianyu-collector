# 1.3.4 发布待办

## P0：更新器完成状态与自动重启

记录时间：2026-09-11

影响版本：从 1.2.0 开始存在“更新完成后仍需用户手动关闭”的流程问题；当前 1.3.3 还存在完成后进度条持续滚动的问题。

### 已确认现象

- 更新检查完成、等待用户点击“立即更新”时，顶部仍显示“回滚保护：检测中…”，容易被误认为更新卡死。
- 更新达到 6/6 并显示“更新完成，当前版本 v1.3.3”后，窗口不会自动退出，也没有明确的完成弹窗或自动重启提示。
- 完成状态下进度条仍保持不确定进度动画并持续刷新。
- 客户端维护包需要在更新器退出后才能替换启动器，但完成事件没有清楚表达“需要关闭并重启客户端”。

### 根因

1. `ProgressBoard.Value` 的 setter 使用 `if (v == value) return;`，比较的是归一化后的新值与 setter 入参本身，导致正常的 `0..100` 赋值全部提前返回；内部值一直保留为 `-1`（不确定进度）。
2. `ProgressBoard` 的 marquee 计时器在构造时永久启动，没有在确定进度或完成状态停止，也没有在控件释放时清理。
3. 更新完成处理只切换为 `Completed` 并显示“关闭”按钮，没有完成提醒、倒计时关闭或自动重启流程。
4. worker 在存在客户端待应用包时仍发送 `completed`，没有发送 C# 更新器已经支持的 `restart_client` 结果，导致 UI 无法区分“全部完成”和“运行时完成、客户端等待重启应用”。
5. 回滚能力只在实际更新阶段计算；检查完成后的 Ready 状态没有更新顶部徽标，所以一直保留初始化文案“检测中…”。

### 1.3.4 必须完成

- 修正进度值比较为与内部字段比较，并在确定进度/完成状态停止 marquee；控件释放时释放计时器。
- Ready 状态改为“已发现更新，等待确认”；回滚徽标改为“将在更新开始后检测”。
- 客户端包进入 pending 时发送 `restart_client`，不得伪装成完全完成。
- 更新成功后将进度固定为 100%，显示明确成功提醒和约 2 秒倒计时。
- 自动关闭更新窗口，应用 pending 客户端包，并自动重新打开新版主启动器。
- 只有失败、回滚失败或需要用户处理时才保留更新窗口。
- 客户端真正应用成功前，不得显示“当前版本已更新”为最终完成状态。

### 发布前验收

- 从 1.2.0 直接升级到 1.3.4：无需手动执行修复脚本，完成后自动重启到新版启动器。
- 从 1.3.3 升级到 1.3.4：完成后进度条停止在 100%，窗口自动关闭并重新打开主启动器。
- 检查阶段、等待确认阶段、执行阶段、客户端待重启阶段和最终完成阶段的文案必须与真实后台状态一致。
- 更新失败时窗口保留，日志和错误码可查看；成功时不遗留 pending ZIP 和旧启动器进程。
- `app/VERSION.txt`、`app/BUILD_ID.txt`、启动器哈希和前端入口哈希全部与 1.3.4 清单一致。
