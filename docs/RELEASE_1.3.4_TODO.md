# 1.3.4 发布待办

## P0：更新器完成状态与自动重启

记录时间：2026-09-11

影响版本：从 1.2.0 开始存在“更新完成后仍需用户手动关闭”的流程问题；当前 1.3.3 还存在完成后进度条持续滚动的问题。

### 已确认现象

- 更新检查完成、等待用户点击“立即更新”时，顶部仍显示“回滚保护：检测中…”，容易被误认为更新卡死。
- 更新达到 6/6 并显示“更新完成，当前版本 v1.3.3”后，窗口不会自动退出，也没有明确的完成弹窗或自动重启提示。
- 完成状态下进度条仍保持不确定进度动画并持续刷新。
- 当前版本和镜像已经匹配时，遗留的 `runtime-sync.pending.json` 仍会让检查结果误报“运行时镜像尚未同步”，界面停留在 2/6 等待再次更新。
- 客户端维护包需要在更新器退出后才能替换启动器，但完成事件没有清楚表达“需要关闭并重启客户端”。
- 新增 P0：从 1.2.0 离线安装包升级后，客户端界面已经显示 1.3.4，但 Docker 仍运行 `local/xianyu/*:1.2.0`，`.env` 仍为 `XR_DEPLOY_MODE=offline`、`XR_IMAGE_TAG=1.2.0`；说明客户端维护包已应用，但运行时镜像同步没有完成。

### 根因

1. `ProgressBoard.Value` 的 setter 使用 `if (v == value) return;`，比较的是归一化后的新值与 setter 入参本身，导致正常的 `0..100` 赋值全部提前返回；内部值一直保留为 `-1`（不确定进度）。
2. `ProgressBoard` 的 marquee 计时器在构造时永久启动，没有在确定进度或完成状态停止，也没有在控件释放时清理。
3. 更新完成处理只切换为 `Completed` 并显示“关闭”按钮，没有完成提醒、倒计时关闭或自动重启流程。
4. worker 在存在客户端待应用包时仍发送 `completed`，没有发送 C# 更新器已经支持的 `restart_client` 结果，导致 UI 无法区分“全部完成”和“运行时完成、客户端等待重启应用”。
5. 回滚能力只在实际更新阶段计算；检查完成后的 Ready 状态没有更新顶部徽标，所以一直保留初始化文案“检测中…”。
6. 运行时同步标记只在 `$runtimeSyncRequired` 为真时删除；当可信离线运行时已经匹配时该值为假，标记因此永久残留并导致每次启动重复提示更新。
7. 离线安装包使用 `-DeferRuntimeImageUpdate` 生成客户端优先更新包。当前流程可能先替换客户端文件并显示新版界面，但没有把后续运行时同步作为同一条强制完成链路；因此客户端版本、`.env` 和 Docker 镜像版本会暂时分裂。

### 1.3.4 必须完成

- 修正进度值比较为与内部字段比较，并在确定进度/完成状态停止 marquee；控件释放时释放计时器。
- Ready 状态改为“已发现更新，等待确认”；回滚徽标改为“将在更新开始后检测”。
- 客户端包进入 pending 时发送 `restart_client`，不得伪装成完全完成。
- 更新成功后将进度固定为 100%，显示明确成功提醒和约 2 秒倒计时。
- 自动关闭更新窗口，应用 pending 客户端包，并自动重新打开新版主启动器。
- 只有失败、回滚失败或需要用户处理时才保留更新窗口。
- 客户端真正应用成功前，不得显示“当前版本已更新”为最终完成状态。
- 可信运行时状态已匹配当前发布版本时自动清理遗留同步标记；再次检查必须返回“当前已是最新版本”，不得停在 2/6。
- 从 1.2.0 离线安装包升级到 1.3.4 或后续版本时，客户端包应用完成后必须自动继续运行时同步：将目标业务镜像拉取/导入到目标版本，更新 `.env` 的部署模式、Registry、Namespace、Tag，重建并校验四个业务容器；在镜像校验完成前不得报告整次升级完成。

### 发布前验收

- 从 1.2.0 直接升级到 1.3.4：无需手动执行修复脚本，完成后自动重启到新版启动器。
- 从 1.3.3 升级到 1.3.4：完成后进度条停止在 100%，窗口自动关闭并重新打开主启动器。
- 检查阶段、等待确认阶段、执行阶段、客户端待重启阶段和最终完成阶段的文案必须与真实后台状态一致。
- 更新失败时窗口保留，日志和错误码可查看；成功时不遗留 pending ZIP 和旧启动器进程。
- `app/VERSION.txt`、`app/BUILD_ID.txt`、启动器哈希和前端入口哈希全部与 1.3.4 清单一致。
- 离线 1.2.0 安装包升级验收必须同时满足：启动器版本为目标版本、`docker compose ps` 的 backend/websocket/scheduler/frontend 镜像全部为目标版本、`.env` 不再保留 `XR_IMAGE_TAG=1.2.0`，并且更新日志包含运行时镜像校验成功记录；不能只检查界面版本。

## P0：VIP 内置 AI 自动回复开关与预置关键词

1.3.3 中 `/api/v1/ai-reply-settings/builtin` 接口会返回成功，但平台 AI 设置的保存函数遗漏了 `builtin_ai_reply_enabled` 字段，导致数据库始终保持关闭。前端又按照请求值提示“已开启”，刷新后开关复原；关键词接口因读取到关闭状态而不返回内置规则。

1.3.4 必须包含以下修复与验收：

- 平台 AI 设置的部分更新必须持久化 `builtin_ai_reply_enabled`，后续保存模型配置时不得把它覆盖。
- 开启/关闭接口和前端提示必须使用数据库最终保存值，禁止乐观显示虚假成功。
- VIP 或管理员开启后，关键词列表应立即显示 336 条内置只读规则；关闭后隐藏内置规则，不影响用户自建关键词。
- 自动回复执行层与关键词列表必须使用同一开关和同一授权判定。
- 蒸馏话术文件必须包含在后端镜像中，发布验收需检查规则加载数量非零。
